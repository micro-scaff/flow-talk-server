# 版本七：扩展能力落地版

## 版本目标

v7 在 v1 到 v6 已完成的 IM 主流程上，补齐四类可直接落地的扩展能力：

- 外部身份系统适配
- 单实例在线状态查询
- 逐条消息送达和已读回执
- MySQL 文本消息搜索

当前版本默认保持项目部署和代码结构简单：Redis 未启用时，实时消息仍由当前进程内的 WebSocket Hub 投递；用户离线或连接在其它进程时，客户端通过历史消息、未读数和消息回执补齐状态。

v7 同时支持可选 Redis。`redis.enabled=true` 后，Redis Pub/Sub 负责跨节点 `message.deliver` 分发，Redis TTL key/ZSET 负责全局在线状态；真实 WebSocket 连接、发送队列和连接生命周期仍由每个进程自己的 `WSHub` 管理。

## 前置基础

- v1 已实现本地用户、注册登录和 JWT 鉴权
- v2 已实现单聊、群聊和会话成员关系
- v3 已实现消息入库、历史消息、会话已读游标和未读数
- v4 已实现单进程 WebSocket 实时投递
- v5 已实现设备记录和最近活跃时间
- v6 已实现群管理、消息撤回和消息删除

## v7.1 外部身份适配

### 接口

```text
POST /api/auth/external
```

请求体：

```json
{
  "provider": "demo",
  "access_token": "external-token"
}
```

成功响应沿用注册和登录接口格式：

```json
{
  "code": 200,
  "data": {
    "user": {
      "id": 10,
      "external_id": "demo:external-token",
      "username": "demo_external-token",
      "nickname": "demo_external-token",
      "avatar_url": "",
      "auth_source": "external",
      "status": 1
    },
    "token": "<jwt-token>"
  },
  "message": "登录成功"
}
```

### 代码方法

- `DemoTokenVerifier.Verify(accessToken string) (ExternalUserProfile, error)`
- `FindUserByExternalID(externalID string) (User, error)`
- `SyncExternalUser(profile ExternalUserProfile) (User, error)`
- `LoginExternalUser(provider string, accessToken string) (User, error)`

### 业务规则

- 当前只实现 `provider = demo`
- `access_token` 去空格后不能为空
- demo provider 生成 `external_id = demo:{access_token}`
- 外部用户首次登录时写入 `users`
- 外部用户再次登录时按 `external_id` 复用同一个内部用户 ID
- 外部用户 `password` 为空，不参与本地账号密码登录
- 外部用户同步时可以刷新 `nickname`、`avatar_url` 和 `status`
- 内部用户被禁用时，即使外部 token 有效，也不能换取 IM token

## v7.2 单实例在线状态

### 接口

```text
GET /api/users/{user_id}/presence
POST /api/users/presence/batch
```

批量查询请求体：

```json
{
  "user_ids": [1, 2, 3]
}
```

响应示例：

```json
{
  "code": 200,
  "data": {
    "user_id": 2,
    "online": true,
    "connection_count": 2,
    "last_active_at": "2026-06-29T12:00:00+08:00",
    "last_seen_at": "2026-06-29T12:00:00+08:00"
  },
  "message": "获取在线状态成功"
}
```

### 数据来源

- `online`：当前进程 `WSHub` 中是否存在该用户连接
- `connection_count`：当前进程内该用户连接数
- `last_active_at`：当前进程内最近一次 WebSocket 活跃时间
- `last_seen_at`：`user_devices.last_seen_at` 中最近一次设备活跃时间

Redis 未启用时，`online`、`connection_count` 和 `last_active_at` 都是本机进程视角，不是全局在线状态。如果用户连接在其它服务实例上，本实例会判断为离线。

Redis 启用后，`online`、`connection_count` 和 `last_active_at` 来自 Redis presence key，表达所有服务实例汇总后的在线状态；`last_seen_at` 仍来自 `user_devices.last_seen_at`。

### 业务规则

- 所有在线状态接口都需要 JWT 鉴权
- `user_id` 必须为正整数
- 批量查询会去重、去掉非法 ID，并按 ID 升序返回
- Redis 未启用时，只表达本服务进程内的在线状态
- Redis 启用时，表达跨服务实例汇总后的在线状态
- 没有设备记录时，`last_seen_at` 返回空字符串
- WebSocket 建连或收到事件时，如果 query 中带 `device_id`，会尝试更新设备最近活跃时间

### Redis 未启用时的多实例问题

当前实现使用进程内 `WSHub` 作为连接缓存：

- 服务节点之间不共享 WebSocket 连接信息
- 任意节点只能查询本节点的在线连接
- 任意节点只能向本节点连接投递实时消息
- 节点重启后，内存中的在线状态会全部丢失
- 异常断线只能依赖当前进程清理，无法为其它节点兜底

这些限制在单实例中是可接受的；多实例部署且 Redis 未启用时，会导致在线状态不准确、跨节点消息无法实时到达，以及 `delivered` 回执可能漏写。

### Redis 落地方案

Redis 可以解决跨节点协同，但不能直接保存真实 WebSocket 连接。WebSocket 连接、socket 句柄和发送队列仍必须保留在本机 `WSHub` 中。

建议按职责拆分：

- 本机 `WSHub`：保存真实 WebSocket 连接、连接发送队列、连接关闭和本机投递
- Redis Pub/Sub：广播跨节点 `message.deliver` 事件，适合实时尽力而为，当前已实现
- Redis Streams：保存可消费的投递事件，适合需要重试、追踪或消费位点的场景，当前未实现
- Redis TTL key：记录连接在线状态，例如 `presence:user:{user_id}:conn:{connection_id}`
- Redis ZSET：按用户维护连接集合或最近活跃时间，便于批量 presence 查询
- MySQL：继续保存消息、会话、成员、已读游标和消息回执等最终状态

当前多实例投递流程：

1. 发送节点调用 `SendMessage` 把消息写入 MySQL。
2. 发送节点返回 `message.ack` 给当前 WebSocket 连接。
3. 发送节点发布 `message.deliver` 到 Redis Pub/Sub。
4. 所有服务节点订阅 Redis 事件。
5. 每个节点只从自己的 `WSHub` 查找本机连接并投递。
6. 投递成功的节点为本机在线接收者写入 `delivered` 回执。

当前全局在线状态流程：

1. WebSocket 建连时，本机 Hub 保存连接，并写入 Redis 在线 key。
2. 收到任意事件或心跳时，刷新 Redis 在线 key 的 TTL 和最近活跃时间。
3. 正常断开时删除 Redis 在线 key。
4. 异常断开时由 Redis TTL 自动过期。
5. `/presence` 查询 Redis 汇总结果，`last_seen_at` 仍从 `user_devices` 读取。

Redis key 示例：

```text
presence:user:{user_id}:conn:{connection_id} -> instance_id, device_id, last_active_at
presence:user:{user_id}:connections -> connection_id set or zset
flow-talk:message_deliver -> Pub/Sub channel
```

TTL 建议略大于客户端心跳间隔。例如客户端每 30 秒心跳一次，Redis 在线 key 可以设置为 60 到 90 秒。这样可以兼顾异常断线自动清理和短暂网络抖动。

## v7.3 精细消息回执

### 数据库

先执行：

- [数据库表创建-消息回执](../数据库/数据库表创建-消息回执.md)

### 接口

```text
GET  /api/messages/{message_id}/receipts
POST /api/messages/{message_id}/delivered
POST /api/messages/{message_id}/read
```

查询回执响应示例：

```json
{
  "code": 200,
  "data": [
    {
      "message_id": 1001,
      "user_id": 2,
      "status": "read",
      "updated_at": "2026-06-29T12:00:00+08:00"
    }
  ],
  "message": "获取消息回执成功"
}
```

### 代码方法

- `UpsertMessageReceipt(messageID int64, userID int64, status string) error`
- `MarkMessageDelivered(messageID int64, userID int64) error`
- `MarkMessageRead(messageID int64, userID int64) error`
- `ListMessageReceipts(requestUserID int64, messageID int64) ([]MessageReceiptDTO, error)`

### 业务规则

- 回执状态只支持 `delivered` 和 `read`
- 写回执前必须确认消息存在
- 写回执前必须确认当前用户是消息所在会话的 active 成员
- 同一 `(message_id, user_id)` 只保留一条回执记录
- `read` 可以覆盖 `delivered`
- 已有 `read` 时，后续 `delivered` 不能降级
- 查询回执前必须确认请求用户是消息所在会话的 active 成员
- WebSocket 投递成功后，服务端会为本机在线接收者尝试写入 `delivered`
- 客户端读到消息后，应主动调用 `POST /api/messages/{message_id}/read`

多实例部署且 Redis 启用时，`delivered` 不再只依赖发送节点的本机在线列表。每个订阅到 Redis 投递事件的节点都会尝试投递自己的本机连接，并为本机在线接收者写入 `delivered`，避免把连接在其它节点的用户漏标为已送达。

## v7.4 消息搜索

### 接口

```text
GET /api/conversations/{conversation_id}/messages/search?q=hello&limit=20
GET /api/messages/search?q=hello&limit=20
```

响应示例：

```json
{
  "code": 200,
  "data": [
    {
      "id": 1001,
      "conversation_id": 1,
      "sender_id": 2,
      "message_type": "text",
      "content": {
        "text": "hello"
      },
      "status": "normal",
      "sent_at": "2026-06-29T12:00:00+08:00"
    }
  ],
  "message": "搜索消息成功"
}
```

### 代码方法

- `SearchConversationMessages(userID int64, conversationID int64, keyword string, limit int) ([]MessageDTO, error)`
- `SearchMyMessages(userID int64, keyword string, limit int) ([]MessageDTO, error)`

### 业务规则

- `q` 去空格后不能为空
- `limit` 默认 `20`，最大 `100`
- 当前只搜索 `message_type = text`
- 当前只返回 `status = normal`
- 会话内搜索必须校验当前用户是该会话 active 成员
- 全局搜索只查当前用户 active 参与的会话
- 搜索使用 MySQL `JSON_EXTRACT(content, '$.text') LIKE ?`
- 搜索关键词通过 SQL 参数传入，不拼接 SQL 字符串

## 验证方式

1. 调用 `POST /api/auth/external`，确认 demo 外部用户可以创建并返回 JWT。
2. 使用同一个 `access_token` 重复调用外部登录，确认返回同一个内部用户 ID。
3. 登录用户建立 WebSocket，调用在线状态接口，确认 `online = true`。
4. 断开 WebSocket 后再次查询，确认 `online = false`，`last_seen_at` 仍来自设备表。
5. 用户 A 发送消息给在线用户 B，查询消息回执，确认 B 可以出现 `delivered`。
6. 用户 B 调用 `POST /api/messages/{message_id}/read`，确认回执状态升级为 `read`。
7. 在会话内搜索文本关键词，确认只返回当前会话的普通文本消息。
8. 调用全局搜索，确认只返回当前用户 active 会话中的普通文本消息。

## 错误处理

- `400`：参数校验失败，例如空 `q`、非法 `user_id`、非法回执状态
- `401`：未登录或登录态失效
- `403`：当前用户不是消息或会话 active 成员
- `404`：消息不存在
- `409`：当前版本暂无 v7 专属冲突场景
- `500`：数据库或服务内部错误
